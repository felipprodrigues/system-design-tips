1. setTimeout, built out of a Promise

Write a setTimeout polyfill using the Promise constructor — and make it cancellable, like the real one.

Plain version: a promise is a receipt. It says "I'll tell you the moment this is done" — but a receipt cannot count seconds. Something else has to own the clock. Working out what owns the clock is the whole exercise.

Work it out

  1. What does setTimeout actually do? Three things: it waits, it calls your function, and it hands back an id so you can cancel. Your version needs all three, so three things to solve.
  2. Can a promise wait? No. A promise does not count time — it sits there doing nothing until somebody calls resolve. So a promise can never be a timer, it can only wrap one. Say that out loud; it is half the grade.
  3. So who waits? Two possible answers, and asking which one they want is the move: wrap the real setTimeout (usually what they mean), or get the time from somewhere else entirely — Date.now(), checked over and over.
  4. The wrapping version writes itself. Put setTimeout inside new Promise and let it call resolve. Then .then() runs the callback.
  5. Now the cancel. Try to cancel a promise — you can't, there is no such button. So you cannot stop the waiting; you can only decide not to act when it finishes. A boolean checked before calling the function does exactly that.
  6. The version with no timer at all. If setTimeout is off the table, you have to keep asking "is it time yet?". A while loop would ask so fast the page freezes — one thread, nothing else gets a turn (§13). requestAnimationFrame asks the same question once per frame and gives the browser its turn in between.

The code

Reading A — wrap it:

const sleep = ms => new Promise(resolve => setTimeout(resolve, ms));

function myTimeout(fn, delay = 0, ...args) {
  let cancelled = false;
  sleep(delay).then(() => { if (!cancelled) fn(...args); });
  return () => { cancelled = true; };   // the clearTimeout equivalent
}

Reading B — no native timer, the real polyfill:

function myTimeout(fn, delay = 0, ...args) {
  let cancelled = false;
  new Promise(resolve => {
    const start = Date.now();
    (function tick() {
      if (cancelled) return;
      if (Date.now() - start >= delay) return resolve();
      requestAnimationFrame(tick);   // yields to the browser, ~16ms granularity
    })();
  }).then(() => { if (!cancelled) fn(...args); });
  return () => { cancelled = true; };
}

Say these while you type

  • requestAnimationFrame, not a while loop — the loop blocks the single thread and nothing else runs, including the paint.
  • Granularity is about 16ms, so the delay is a floor, never a guarantee. Real setTimeout has the same caveat.
  • The returned cancel function is why the real setTimeout hands back an id in the first place.

2. A timer with Start, Pause and Reset

Build a React timer component with Start, Pause and Reset buttons.

Plain version: a stopwatch is only two facts — a number, and whether it is currently counting. Every button just changes one of those two.

Work it out

  1. What has to be remembered? The elapsed time, and whether it is running. That is two useState. If you reach for a third, you are probably storing something you could compute instead.
  2. Who makes the number go up? Something repeating: setInterval, ticking every 100ms.
  3. Where does the interval live? Not in the Start handler. Starting a timer is a side effect that later has to be torn down, so it belongs in useEffect with running as the dependency: created when running turns true, destroyed when it turns false.
  4. Here is the trap. Write setMs(ms + 100) and the interval callback remembers the ms from the render that created it — forever. The display goes 0 → 100 → 100 → 100. The updater form setMs(m => m + 100) is handed the current value instead of remembering an old one. This is the bug they are hunting for.
  5. What stops it? The function you return from the effect. It runs on pause and on unmount. Skip it and the interval keeps ticking after the component is gone — and in dev StrictMode you get two of them.
  6. Now the buttons are trivial. Start sets running true, Pause sets it false, Reset sets it false and the number back to zero.

The code

function Timer() {
  const [ms, setMs] = useState(0);
  const [running, setRunning] = useState(false);

  useEffect(() => {
    if (!running) return;
    const id = setInterval(() => setMs(m => m + 100), 100);
    return () => clearInterval(id);
  }, [running]);

  const s = (ms / 1000).toFixed(1);

  return (
    <div>
      <output aria-live="polite">{s}s</output>
      <button onClick={() => setRunning(true)}  disabled={running}>Start</button>
      <button onClick={() => setRunning(false)} disabled={!running}>Pause</button>
      <button onClick={() => { setRunning(false); setMs(0); }}>Reset</button>
    </div>
  );
}

If they ask you to improve it

"setInterval drifts — the browser is free to run it late, and the error accumulates. For a real stopwatch I would store startedAt and accumulated, then compute Date.now() - startedAt + accumulated on every tick. The interval becomes a repaint trigger rather than the source of truth, so being late once costs nothing."

3. Event loop — the trace

Analogy (full version in §13): one cashier, two lines. The promise line must be completely empty before the cashier even glances at the timer line. Every "what is the output order?" question is that one rule applied.

Memorize the order, then narrate it: all sync code → drain all microtasks (promise .then, queueMicrotask) → one macrotask (setTimeout) → drain microtasks again → repeat.

console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve().then(() => console.log('3'));
(async () => { console.log('4'); await null; console.log('5'); })();
console.log('6');

→ 1, 4, 6, 3, 5, 2

4 is sync (async function bodies run synchronously until the first await). await null suspends and the rest becomes a microtask, queued after the already-queued 3. 2 is last because timers are macrotasks — 0ms means "soonest available turn," not "now."

If they ask about Node: process.nextTick jumps the microtask queue ahead of promises.

5. A list you can add to and delete from

Render a list with a text input: typing and submitting adds an item, each row can be deleted.

Plain version: the list is a box of cards. Adding an item means making a new box with one more card in it — not scribbling on the box you already have. React only notices new boxes.

Work it out

  1. What is state? Two things: the array of items, and the text currently typed in the input.
  2. Every item needs a name tag. Give each one an id the moment it is created (crypto.randomUUID()). React needs a stable key, and the position in the array is not stable — delete the first row and every other row's position shifts.
  3. Why not push? React decides whether to re-render by comparing the old value to the new one. Push mutates the same array, so the two are the same object, so React sees no change. Build a new array instead: [...prev, item].
  4. Guard the empty input. Trim the text, bail out if nothing is left. Small, and they are watching for it.
  5. Deleting is the same idea in reverse. filter returns a new array without the matching id. Still no mutation.
  6. Use the state updater form (setItems(prev => …)) rather than reading items directly — same reason as the timer, it cannot go stale.

The code

const [items, setItems] = useState([]);
const [text, setText] = useState('');

const add = e => {
  e.preventDefault();
  const v = text.trim();
  if (!v) return;                     // empty-input guard — say it out loud
  setItems(prev => [...prev, { id: crypto.randomUUID(), text: v }]);
  setText('');
};

const remove = id => setItems(prev => prev.filter(i => i.id !== id));

The free points

  • key={item.id}, never the index. With index keys React reuses the wrong DOM node when a row is removed, so anything living in that node — a focused input, a half-typed value — attaches to the wrong row.
  • Wrap it in a <form> and Enter submits for free.
  • An aria-label on each delete button, or the whole list sounds like "button, button, button".
  • Close with: "next I would add a test for add-then-delete."

7. Closures

Analogy: a closure is a function that leaves the room carrying a backpack. Whatever variables were in scope when it was created go with it wherever it is called, and nobody outside can reach into the bag. That is both the feature (private state) and the leak (the bag stays packed as long as the function is alive).

Definition to say verbatim: "A closure is a function bundled with the scope it was created in. The inner function keeps a live reference to those variables, so they survive after the outer function returns."

function counter() {
  let count = 0;              // not GC'd — the returned fns reference it
  return {
    inc: () => ++count,
    get: () => count,
  };
}

const c = counter();
c.inc(); c.inc();
c.get();   // 2
// count is unreachable from outside — closures are JS's original private state

Three points that separate a junior answer from a senior one:

  1. Live reference, not a snapshot. This is the var-in-a-loop bug from §15 — all three callbacks close over the same i and read it after it became 3.
  2. Each call creates a new scope. const a = counter(), b = counter(); — a.inc() leaves b at 0. Independent counts.
  3. It is a memory tradeoff. Closures keep their scope alive, so a long-lived closure over something large — a DOM node, a big array — is a leak. That is why you clear timer ids and remove listeners in cleanup.

Real uses, pick two: debounce/throttle, module privacy, memoization, partial application.

const memoize = fn => {
  const cache = new Map();                   // private, persists across calls
  return x => cache.has(x) ? cache.get(x) : (cache.set(x, fn(x)), cache.get(x));
};
Bonus tie-in: "Every React hook is a closure. useState returns a setter closed over the component's slot, and the stale-closure bug in that Timer is exactly this mechanic."

8. Core Web Vitals

What they actually are

Web Vitals are Google's attempt to turn "does this site feel good to use?" into numbers you can measure.

Before them, people measured things like "page load time" or DOMContentLoaded. The problem: those do not match what users experience. A page can fire load in 800ms and still feel broken — blank for two seconds, then text jumping around while you try to tap a button. The metric said "fast," the human said "garbage."

So Google picked three questions a real user implicitly asks, and defined one metric per question:

The user's questionMetric
"Is it there yet?"LCP — loading
"Does it respond when I touch it?"INP — interactivity
"Will it stop moving so I can read it?"CLS — visual stability

Those three are the Core Web Vitals. "Web Vitals" is the larger family; the Core three are the subset Google committed to as stable and universally applicable — and the subset that feeds Google Search ranking as part of the page experience signal. That last part is why product managers care, and why this question shows up in interviews.

The three, explained

LCP — Largest Contentful Paint. When did the biggest visible thing finish rendering? Not the first pixel, not the full load — the moment the largest element in the viewport (usually a hero image, a video poster, or a big block of text) appears. Google's reasoning: that element is a good proxy for "the page is now useful." A spinner appearing fast does not help anyone.

INP — Interaction to Next Paint. You clicked. How long until the screen changed? It measures the full round trip: the delay before your handler could even start, plus the handler running, plus React re-rendering, plus the browser painting the result. It reports roughly the worst interaction of the whole visit, because one 900ms freeze is what the user remembers.

CLS — Cumulative Layout Shift. Did content move after you had started reading it? An unitless score, not a time. It accumulates every unexpected shift — an image loading without reserved dimensions and shoving the paragraph down, a banner injecting itself above the content, a font swapping and reflowing the text. The canonical pain: you go to tap a link, an ad loads, and you tap something else.

Thresholds

MetricMeasuresGoodNeeds workPoor
LCP Largest Contentful PaintLoading — when the biggest element renders≤ 2.5s≤ 4s> 4s
INP Interaction to Next PaintResponsiveness — worst interaction latency over the visit≤ 200ms≤ 500ms> 500ms

Say this and you sound current: "INP replaced FID in March 2024. FID only measured the delay before the first handler started — INP measures full input-to-paint time across all interactions, so it actually catches slow rendering."

Supporting metrics: TTFB (server/network), FCP (first pixel). Not Core Vitals, but they are how you diagnose a bad LCP.

Fixes — have one per metric:

  • LCP → almost always the hero image or a blocking resource. <img fetchpriority="high">, preload the LCP asset, modern formats, no lazy-loading above the fold, cut render-blocking CSS/JS, CDN.
  • INP → long tasks hogging the main thread. Break them up (scheduler.yield), move work off the main thread, debounce input handlers, trim hydration cost.
  • CLS → reserve space. width/height on images, min-height on ad/embed slots, font-display: optional or preloaded fonts, never inject content above existing content.

The part people get wrong: field vs lab

They are real-user metrics, not lab metrics.

When Google evaluates your site it uses the 75th percentile of actual visits from the Chrome User Experience Report (CrUX) — real people on real devices and real networks, split by mobile and desktop. The 75th percentile means three out of four visits must hit "good." You cannot pass by averaging away the bad sessions, and you cannot pass on your own fast laptop.

That gives you two kinds of data, and knowing the difference separates a memorized answer from an understood one:

  • Lab data — Lighthouse, DevTools, CI. Synthetic, reproducible, great for debugging a cause. But it cannot measure INP properly, because nothing is actually clicking.
  • Field data — CrUX, the web-vitals npm library, your RUM tool. Messy, real, and the only thing that counts.
import { onLCP, onINP, onCLS } from 'web-vitals';
onLCP(sendToAnalytics); onINP(sendToAnalytics); onCLS(sendToAnalytics);

So the workflow is: field data tells you that you have a problem and where; lab data tells you why. Chasing a Lighthouse score in isolation is the classic mistake — you optimize a number nobody is experiencing.

Why they are designed this way

The three are not arbitrary — they are deliberately orthogonal. Each maps to a different failure mode with a different root cause and a different fix:

  • LCP is a network and resource-priority problem → preload, CDN, compress, do not block the parser.
  • INP is a main-thread problem → your JavaScript is doing too much in one task.
  • CLS is a layout problem → you did not reserve space for things that arrive late.

You can be perfect at one and terrible at another, which is the point. A single blended "performance score" would hide exactly which of the three is hurting your users.

The one sentence to say in the interview: "Web Vitals are standardized, field-measured proxies for perceived user experience — loading, responsiveness and visual stability — scored at the 75th percentile of real users, which is why I measure in production and only use Lighthouse to diagnose."

9. WebSockets

Analogy: HTTP is sending letters. You write, you wait for a reply, and every letter needs its own envelope, stamp and address. A WebSocket is a phone call you leave open: you pay the setup cost once, then either side just talks whenever it has something to say — no envelope, no waiting to be asked.

Full-duplex, persistent, bidirectional connection over a single TCP socket. Starts as an HTTP GET with Upgrade: websocket, the server answers 101 Switching Protocols, then both sides send frames whenever they want — no request needed.

const ws = new WebSocket('wss://api.example.com/feed');  // wss = TLS, always

ws.onopen    = () => ws.send(JSON.stringify({ type: 'subscribe', room: 'general' }));
ws.onmessage = e => setMessages(prev => [...prev, JSON.parse(e.data)]);
ws.onerror   = err => console.error(err);
ws.onclose   = e => { if (!e.wasClean) reconnect(); };   // they WILL ask about this

In React:

useEffect(() => {
  const ws = new WebSocket(url);
  ws.onmessage = e => setMessages(prev => [...prev, JSON.parse(e.data)]);
  return () => ws.close();     // cleanup, same reflex as clearInterval
}, [url]);

Volunteer these three — it is what they are probing for:

  1. Reconnect with exponential backoff + jitter. Connections die on wifi drops, proxies, mobile sleep. Naive instant retry means you DDoS your own server when it restarts.
  2. Heartbeat / ping-pong. A dead TCP connection can look open for minutes. Ping on an interval, drop and reconnect on no pong.
  3. Auth. The browser WebSocket API cannot set headers, so no bearer token on the handshake — pass a short-lived ticket in the query string, or authenticate in the first message after open.

Scaling is the hard part. Stateful connections pin users to a server, so you need sticky sessions and a pub/sub backplane (Redis) to fan messages across instances. HTTP is stateless and trivially load-balanced; that is the real cost of WebSockets.

Letters versus an open phone line (§9). A product page wants letters — each one is self-contained, so a CDN can photocopy it and hand it to the next thousand people. A chat app wants the phone line, because the other side needs to speak first and you cannot photocopy a conversation.

One-sentence answer: "HTTP is request/response and stateless — the client has to ask. WebSockets keep one connection open so the server can push. I reach for WebSockets when the server needs to initiate, and stay on HTTP otherwise, because statelessness buys caching, CDNs and trivial scaling."

Then show the middle ground — this is the senior signal:

  • Polling — request every N seconds. Simple, but wasted requests and up-to-N-seconds stale.
  • Long polling — server holds the request open until there is data. The pre-WebSocket fallback.
  • SSE (EventSource) — server→client push over plain HTTP. One-directional, auto-reconnects for free, works through any HTTP infrastructure. Say this out loud: if I only need server→client — notifications, live prices, LLM token streaming — SSE is the lazier right answer. WebSockets are for genuinely bidirectional traffic.
  • WebRTC — peer-to-peer, for media.

"Which would you pick?" Chat / collaborative editing / multiplayer / live cursors → WebSocket. Notifications / feed updates / AI streaming → SSE. CRUD → HTTP. "Updates every 30s is fine" → polling, and do not apologize for it.

11. Web Workers

Analogy: your app is a one-person kitchen. The chef (main thread) takes orders, cooks and plates. If the chef starts peeling 10,000 potatoes, nobody gets served — the UI freezes. A Web Worker is a prep cook in a separate room: you hand them potatoes through a window (postMessage), they hand back the peeled result. They cannot touch the dining room — no DOM, no window — and they only communicate through the window, never by sharing the same cutting board.
// worker.js
self.onmessage = e => self.postMessage(heavyCrunch(e.data));

// main.js
const w = new Worker('/worker.js');
w.postMessage(bigArray);
w.onmessage = e => setResult(e.data);
// cleanup: w.terminate()

Key facts: separate thread, separate global scope. No DOM/window/document. Data is copied via structured clone, not shared — so passing a 100MB array has a cost; use Transferable/ArrayBuffer transfer or SharedArrayBuffer to avoid the copy.

Use for: parsing huge JSON, image/video processing, crypto, heavy computation. Do not use for network calls — fetch is already async and non-blocking, a worker adds nothing.

Siblings worth naming: Service Worker = a network proxy for offline/caching (different purpose, same thread model). Worklets = tiny workers for CSS/audio.

12. Webpack

Analogy: a factory assembly line for your source files. Raw materials go in one end, a boxed product comes out the other.
  • Entry — where the line starts (src/index.js).
  • Module graph — Webpack follows every import to build a dependency tree.
  • Loaders — the stations on the line. Each transforms one file type: babel-loader, css-loader, ts-loader. Loaders work on individual files.
  • Plugins — the floor supervisors. They hook into the whole build: HtmlWebpackPlugin, MiniCssExtractPlugin, DefinePlugin.
  • Output — the boxed bundles, hashed for cache-busting (main.[contenthash].js).
Remember it as: loaders transform files, plugins transform the build. That one sentence is the most-asked distinction.

Also know: tree shaking (dead-code elimination; requires ESM import/export — does not work with CommonJS require), code splitting (§23), HMR in dev, source maps for prod debugging. Have an opinion ready: "Vite/esbuild/Turbopack are faster because they are Go/Rust and use native ESM in dev instead of bundling on every change — Webpack is still what most legacy enterprise builds run on."

13. Event loop — the deep version

Analogy: a single cashier with two lines. The cashier (call stack) serves one customer at a time. The VIP line (microtasks: promises, queueMicrotask, MutationObserver) must be completely empty before the cashier looks at the regular line (macrotasks: setTimeout, setInterval, I/O, events). And after serving one regular customer, they check the VIP line again — and drain it fully.

The loop, in order:

  1. Run the current script to completion (call stack empties).
  2. Drain the entire microtask queue — including microtasks queued by microtasks. (Infinite microtasks = permanent freeze; the loop never moves on.)
  3. Take one macrotask. Run it.
  4. Drain microtasks again.
  5. Render (requestAnimationFrame → style → layout → paint), roughly once per frame.
  6. Repeat.

The render step at #5 is why setTimeout(fn, 0) is not "now" — it is "after this task, its microtasks, and possibly a paint."

Practice trace:

console.log('A');
setTimeout(() => { console.log('B'); Promise.resolve().then(() => console.log('C')); }, 0);
Promise.resolve().then(() => { console.log('D'); setTimeout(() => console.log('E'), 0); });
queueMicrotask(() => console.log('F'));
console.log('G');

→ A, G, D, F, B, C, E

Walk it: A, G sync. Microtasks drain: D (which queues timer E), then F. First macrotask: B, which queues microtask C — drained immediately after that task. Then the next macrotask: E.

Node adds: process.nextTick runs before the promise microtask queue, and macrotasks split into phases (timers → pending → poll → check/setImmediate → close).

14. Deep vs shallow copy

Analogy: shallow copy = photocopying a page that has addresses written on it. You get a new page, but both pages point to the same houses. Deep copy = rebuilding the houses too.
const original = { name: 'a', config: { theme: 'dark' } };

const shallow = { ...original };          // or Object.assign({}, original)
shallow.name = 'b';                       // OK — original.name unchanged
shallow.config.theme = 'light';           // BUG — original.config.theme is now 'light'

const deep = structuredClone(original);   // modern, native, use this
deep.config.theme = 'blue';               // original untouched

Shallow: spread, Object.assign, slice, Array.from, arr.map(x => x). Copies one level; nested objects/arrays stay shared by reference.

Deep: structuredClone() — native, handles Date, Map, Set, RegExp, circular references. The old JSON.parse(JSON.stringify(obj)) trick is the one to criticize: it drops undefined, functions and Symbols, turns Date into a string, throws on circular refs, and mangles NaN/Infinity into null. Lodash cloneDeep if you are on an old target.

Why React cares: "React compares by reference. state.items.push(x); setState(state) does nothing — same reference, no re-render. That is why you spread into a new array. But a shallow copy of nested state is not enough either — if I mutate copy.config I have mutated the original and broken time-travel debugging. That is the case for Immer or structuredClone."

The same leak, in a loop: this is the closure question they pair it with.

for (var i = 0; i < 3; i++) setTimeout(() => console.log(i)); // 3,3,3
for (let i = 0; i < 3; i++) setTimeout(() => console.log(i)); // 0,1,2
Analogy: var gives the whole loop one whiteboard to write on. By the time anyone gets around to reading it, it says 3. let hands each iteration its own sticky note, so each callback reads its own copy.

One shared var binding, mutated to 3 before any callback runs; let creates a fresh binding per iteration. The pre-let fix was an IIFE. Closures themselves are §7.

The const gotcha they always ask: const freezes the binding, not the value.

const arr = [1, 2];
arr.push(3);     // fine — mutating the object, not rebinding
arr = [];        // TypeError: Assignment to constant variable
// want immutability? Object.freeze(arr) — and that is shallow too (see §14)
TDZ in one line: "let/const are hoisted, but reading them before the declaration throws instead of giving undefined. That gap is the Temporal Dead Zone — it turns a silent bug into a loud one."

Default to const, use let when you must reassign, never var.

16. Writing a polyfill

What is a polyfill, and how would you write one — say Array.prototype.flat or Function.prototype.bind?

Plain version: a polyfill is a travel plug adapter. Your device expects a socket shape this country does not have, so you carry a small part that provides it. Transpiling is a different thing — that is rebuilding the device to run on the local voltage.

Work it out

  1. First decide what is actually missing. A missing thing (Promise, fetch, .includes) needs a polyfill. Unsupported grammar (arrow functions, async/await) needs Babel. Babel cannot polyfill Promise — there is no syntax to rewrite, the object simply is not there. Saying this split out loud is most of the answer.
  2. Where does the new method go? On the prototype, so every array (or every function) gets it — that is what Array.prototype.flat means.
  3. Check before you write. if (!Array.prototype.flat). Never clobber a native implementation: it is faster and it is correct.
  4. Hide it. A plain assignment creates an enumerable property, so it starts appearing in anyone's for…in loop over an array. Object.defineProperty with enumerable: false is how the real ones are defined.
  5. Inside the method, this is the instance — the array you called it on, or the function being bound. That one fact is the whole trick to bind: capture this in a variable, return a new function that applys it later with the context you were given.
  6. Then the edge cases they are listening for: sparse arrays have holes, so map must skip indices that do not exist (if (i in this)); and a bound function can still receive more arguments at call time, so the bound ones go first and the rest follow.

The code

if (!Array.prototype.myFlat) {
  Object.defineProperty(Array.prototype, 'myFlat', {
    value: function (depth = 1) {
      return this.reduce((acc, v) =>
        acc.concat(Array.isArray(v) && depth > 0 ? v.myFlat(depth - 1) : v), []);
    },
    enumerable: false,   // or it shows up in for...in and breaks the world
  });

Function.prototype.myBind = function (ctx, ...bound) {

17. Frontend vulnerabilities

The two big ones in one line each. XSS is a stranger getting to write on your page — once their script runs, it runs with your page's permissions, so it can read the user's token. CSRF is a stranger getting the user's browser to sign something on their behalf — the browser helpfully attaches the session cookie to a request it had no idea was hostile. "Their code in my page" versus "my credentials on their request."

XSS (Cross-Site Scripting) — attacker gets their JS to run in your page, then reads tokens and acts as the user. Three kinds: stored, reflected, DOM-based. Fix: never interpolate untrusted strings into HTML. In React {userInput} is auto-escaped — the holes are dangerouslySetInnerHTML (sanitize with DOMPurify first) and href={userInput} allowing javascript:. Add a Content Security Policy as defense-in-depth.

CSRF (Cross-Site Request Forgery) — a different site makes the browser send an authenticated request using your cookies. Fix: SameSite=Lax/Strict cookies, CSRF tokens, check Origin.

Token storage — localStorage is readable by any XSS. Prefer httpOnly, Secure, SameSite cookies for session tokens; keep access tokens short-lived.

Others worth naming: clickjacking (X-Frame-Options/frame-ancestors), open redirect (validate targets against an allowlist), dependency/supply-chain risk (npm audit, lockfiles, Dependabot), secrets committed to a repo or leaked into a client bundle (anything in NEXT_PUBLIC_* is public), insecure direct object reference — authorization belongs on the server; hiding a button is not access control.

The sentence that lands: "Client-side validation is UX. Server-side validation is security. Never trust the client."

18. Virtual DOM — deep

Analogy: you are renovating a room. You do not demolish and rebuild it to move one chair. You draw a new blueprint, compare it to the old blueprint, and send the builders a list containing only "move the chair." The blueprints are cheap paper (JS objects); the builders are expensive (DOM writes that trigger layout and paint).

The Virtual DOM is a tree of plain JS objects describing what the UI should look like:

// <button className="x">Hi</button> compiles to roughly:
{ type: 'button', props: { className: 'x', children: 'Hi' } }

The cycle: state changes → your component function re-runs → returns a new VDOM tree → React diffs it against the previous tree → computes the minimum set of real DOM mutations → flushes them in one batch.

Why it is faster: it is not faster than hand-written optimal DOM code. It is faster than the naive alternative (re-render everything) and it batches writes to avoid layout thrashing. The real selling point is declarative programming with acceptable performance — you describe the end state instead of writing imperative transition steps.

Say this to show range: "Svelte and Solid skip the VDOM entirely — they compile to targeted updates at build time. The VDOM is a tradeoff, not a law of physics."

19. Diffing, reconciliation, Fiber

Analogy: §18 was "compare the blueprints." This is how the comparison is run. Imagine the renovation list is huge and the client keeps walking in with urgent changes. The old React read the list top to bottom without looking up — once it started, it finished, and the client waited. Fiber turned the list into individual numbered tickets, so React can do one, check whether anything more urgent came in, and reshuffle the rest. Same comparison, interruptible delivery.

Reconciliation is the whole algorithm for syncing the new tree to the old. Diffing is the comparison step inside it. Fiber is the data structure and scheduler that runs it.

Diffing heuristics — React does not do a full O(n³) tree diff; it does O(n) using two assumptions:

  1. Different element type → destroy and rebuild that whole subtree. <div> becomes <span>, or <ComponentA> becomes <ComponentB> → the old node and all its state are thrown away. Same type → keep the DOM node, update only the changed props.
  2. Keys identify children across renders. Same key = same component, just moved. This is the real answer to "why not index keys": with index keys, deleting the first item shifts every subsequent key, so React thinks the content changed rather than that one item was removed — it reuses the wrong DOM nodes and your uncontrolled input values land on the wrong rows.

Fiber (React 16+) — the old reconciler recursed through the tree synchronously and could not be stopped, so a big update blocked the main thread and dropped frames. Fiber restructured the tree into a linked list of units of work (child, sibling, return pointers) so the work becomes a loop instead of recursion — meaning React can pause, resume, reprioritize and abandon work.

Two phases, worth naming:

  • Render / reconcile phase — interruptible, builds the work-in-progress tree, no DOM touched, can be thrown away. This is why render must be pure and why StrictMode double-invokes it.
  • Commit phase — synchronous, uncancellable, applies mutations and runs effects.

That split powers Concurrent features: useTransition, useDeferredValue, Suspense, time-slicing. A high-priority keystroke can interrupt a low-priority list re-render.

20. How HTML and CSS get to the screen

Analogy: building a room. HTML is the list of furniture, CSS is the instructions for how it should look. The browser will not let anyone in until it has both — that is why CSS is render-blocking; it refuses to show you a half-decorated room. Then it works out where each piece goes (layout), fills in the colours (paint), and finally opens the door (composite).

The Critical Rendering Path, in order:

  1. HTML → DOM. The parser streams the bytes and builds the DOM tree incrementally.
  2. CSS → CSSOM. CSS is render-blocking — the browser will not paint until it is parsed, because it refuses to show unstyled content (FOUC).
  3. Render tree = DOM + CSSOM, with non-visual nodes dropped (display: none nodes are excluded; visibility: hidden ones stay — they occupy space).
  4. Layout / reflow — compute geometry: position and size of every box.
  5. Paint — fill in pixels: colors, text, shadows, borders.
  6. Composite — assemble layers on the GPU and put them on screen.

The scripts part — most-asked detail: a plain <script> blocks HTML parsing while it downloads and executes (which is why scripts traditionally go before </body>). defer = download in parallel, execute after parsing, in order. async = download in parallel, execute the moment it arrives, order not guaranteed. Rule of thumb: defer for anything that touches the DOM, async for independent things like analytics.

Performance consequence to volunteer: changing geometry (width, top, margin) triggers layout → paint → composite. Changing color/background skips layout. Changing transform and opacity only composites — GPU, no layout, no paint. "That is why I animate transform instead of left, and why reading offsetHeight in a loop after writing styles causes layout thrashing — each read forces a synchronous recalculation."

22. useMemo and useCallback

Analogy: both are a note on the fridge saying "already did this, here is the answer." Useful when the task was genuinely expensive. Silly when the task was "add two numbers" — now you are paying for the note, the fridge space and the act of reading it, every single time, to avoid doing something that was free. That is most memoization in real codebases.

useMemo caches a value. useCallback caches a function reference. Both are referential-stability tools first, speed tools second.

const sorted = useMemo(() => items.sort(cmp), [items]);   // skip expensive recompute
const onPick = useCallback(id => setSel(id), []);         // stable identity for children
The honest answer — lead with this: "They are not free. Every memo costs memory plus a dependency comparison on each render, and the hook itself has to run regardless. I profile first. Most useCallbacks I see in code review are doing nothing because the child is not memoized — so the new function reference would not have caused a re-render anyway."

The three cases where they genuinely earn their place:

  1. Passing a callback to a React.memo'd child. Without useCallback, a fresh function every render breaks the memo entirely — you paid for memo and got nothing.
  2. Genuinely expensive computation — sorting/filtering thousands of rows, parsing, heavy derivation.
  3. A value in another hook's dependency array — an unstable object or function there makes useEffect re-fire every render (a classic infinite-loop source).

React.memo completes the trio: it shallow-compares props and skips the re-render. All three only matter together.

Modern coda: "the React Compiler in React 19 auto-memoizes, which makes most manual useMemo/useCallback unnecessary going forward."

23. Code splitting

Analogy: you are flying somewhere for the weekend. Code splitting is not packing your whole wardrobe. Take what you need on arrival; have the rest shipped only if you actually go somewhere that needs it. The user who only visits the homepage should never download the admin dashboard.

Ship less JavaScript up front. Split along two axes.

By route — highest value, nearly free:

const Settings = lazy(() => import('./Settings'));
<Suspense fallback={<Spinner />}><Settings /></Suspense>

By interaction — load on demand, not at startup:

const onOpen = async () => {
  const { Editor } = await import('./HeavyEditor');  // dynamic import = a split point
  setEditor(Editor);
};

import() returns a Promise and tells the bundler "make this a separate chunk." Next.js splits by route automatically; next/dynamic adds component-level splitting with ssr: false as an option.

Round it out with: vendor chunking (splitChunks) so library code caches separately from app code, tree shaking to drop unused exports, contenthash filenames so a deploy does not bust every cached chunk, and prefetching the next likely route on hover/idle so splitting does not trade startup time for click latency. 24. Measuring React performance

The rule before any of the tooling: you cannot fix what you have not located. "The app feels slow" is a symptom with at least three unrelated causes (§34), and guessing between them is how people end up sprinkling useMemo on components that were never the problem. So the answer to this question is a sequence, not a tool.

Order of operations: React DevTools Profiler → record an interaction → read the flamegraph.

  • Flamegraph — width = render duration. Wide bars are your problem.
  • Ranked view — slowest components first.
  • "Highlight updates when components render" — fastest way to spot a component re-rendering for no reason.
  • "Record why each component rendered" — tells you whether it was props, state, hooks, or a parent re-render. This is the setting that actually finds the bug.

The <Profiler> component for programmatic/CI measurement:

<Profiler id="List" onRender={(id, phase, actualDuration) => log({ id, phase, actualDuration })}>

Then Chrome DevTools Performance for the full picture — long tasks, main-thread blocking, layout thrashing — plus Lighthouse for Web Vitals (§8) and the bundle analyzer for ship-size.

The three re-render causes to recite: state changed, props changed, or the parent re-rendered. Common fixes: lift state down (move it to the component that actually uses it so the re-render has a smaller footprint), React.memo the expensive child, split context so unrelated consumers do not wake up, virtualize long lists (react-window / TanStack Virtual), and use useDeferredValue/useTransition to keep typing responsive while a heavy list catches up.

25. useRef

Analogy: a ref is a pocket. You can put something in it and take it out later, it stays with you across re-renders — and nobody can see what is in it, so putting something in does not change how you look. useState is the opposite: it is what you are wearing, so changing it means everyone sees a new you (a re-render).

Two jobs, one hook.

1. A box for mutable state that must NOT trigger re-renders.

const timerId = useRef(null);
timerId.current = setInterval(tick, 1000);   // mutating .current never re-renders

2. A handle on a DOM node.

const inputRef = useRef(null);
useEffect(() => inputRef.current?.focus(), []);
return <input ref={inputRef} />;
The defining comparison: "useState is for values the UI displays — changing it re-renders. useRef is for values the UI does not display — changing it does not. And unlike a plain local variable, a ref survives re-renders, because the same object persists for the component's whole life."

Typical uses: timer/interval ids, AbortControllers, WebSocket instances, previous-value tracking, "has this mounted yet" flags, and the escape hatch for the stale-closure problem — a ref always reads the latest value because you read .current at call time rather than closing over a snapshot.

Rules: never read or write .current during render (it is a side effect and breaks concurrent rendering) — do it in effects and handlers. Refs are populated after the DOM is committed, so a ref is null on the first render pass.

26. Throttle (and debounce)

Implement throttle. What is the difference between throttling and debouncing, and when do you use each?

Plain version: debounce is an elevator — someone keeps stepping in, the doors keep reopening, and it only departs once there is a pause. Throttle is a subway timetable — a train leaves every five minutes no matter how many people turn up.

Work it out

  1. Which one does this situation want? Only the final value matters → debounce (search box, autosave, validation). The values along the way matter but not all of them → throttle (scroll position, mousemove, drag).
  2. What does throttle have to remember? When it last fired. That has to survive between calls but stay private — so the function returns a function, and the memory lives in the closure between them.
  3. The first call. Nothing has fired yet, so fire immediately. That is the leading edge.
  4. A call that comes too soon. The lazy answer is to drop it. But think about which event that throws away: the very last one of the burst — the position where the user actually stopped scrolling. Dropping it is the bug.
  5. So park it instead. Schedule it for the moment the window reopens. That is the trailing edge.
  6. And keep replacing it. Every early call clears the pending one and schedules itself, so whatever happened last is what eventually fires.

The code

const throttle = (fn, ms) => {
  let last = 0, timer;
  return (...args) => {
    const now = Date.now(), remaining = ms - (now - last);
    if (remaining <= 0) { last = now; fn(...args); }    // leading edge
    else {                                              // trailing edge:
      clearTimeout(timer);                              // do not drop the last call
      timer = setTimeout(() => { last = Date.now(); fn(...args); }, remaining);
    }
  };
};

Two things to add unprompted

  • The leading vs trailing edge distinction, as above — a naive throttle silently discards the one event you care about.
  • The native alternative: "for scroll-triggered work I reach for IntersectionObserver before throttling a scroll listener — the browser does that off the main thread."

27. call, apply, bind

Analogy: a function like greet() says "Hi, my name is …" without knowing whose mouth it is in. These three decide who is speaking. call and apply say it right now on someone's behalf (the only difference is whether you hand over the words loose or in a bag). bind does not say anything — it hands you back a new function that is permanently that person's, to use whenever.

All three set this. Mnemonic: C for Comma, A for Array, B for Bind-later.

const greet = function (greeting, punct) { return `${greeting}, ${this.name}${punct}`; };
const user = { name: 'Ada' };

greet.call(user, 'Hi', '!');      // 'Hi, Ada!'  — args comma-separated, invokes now
greet.apply(user, ['Hi', '!']);   // 'Hi, Ada!'  — args as an array, invokes now
const bound = greet.bind(user, 'Hi');
bound('!');                       // 'Hi, Ada!'  — new function, call it later

call/apply invoke immediately. bind returns a new permanently-bound function (and supports partial application — pre-filling leading arguments). A bound function cannot be rebound; new on it is the one exception.

Why it still comes up: arrow functions have no this of their own — they inherit it lexically, which is why this bugs and .bind(this) in constructors mostly vanished with hooks and arrows. Borrowing array methods is the other classic: Array.prototype.slice.call(arguments) to turn arguments into a real array (modern: [...arguments] or just rest params). See the bind polyfill in §16 — writing it proves you understand closures and this in one answer.

28. A useDebounce hook, and why cleanup matters

Write a useDebounce hook for a search box — one request after the user stops typing, not one per keystroke. Then explain cleanup in React.

Plain version: every keystroke restarts a short countdown. Stop typing long enough for a countdown to actually finish, and the value goes through. The restarting is the entire hook.

Work it out

  1. What should the hook give back? A second, slower copy of the value. The input keeps using the fast one so typing never lags; the fetch uses the slow one.
  2. What makes the copy slower? A setTimeout that copies value into the slow state after delay milliseconds.
  3. Now the hard part — who cancels the previous countdown? Instinct says track the timer id yourself and clear it on the next keystroke. You don't have to.
  4. React already does it. An effect's cleanup runs before the next run of that effect, not only on unmount. So returning clearTimeout(id) means every change to value cancels the pending copy and starts a fresh one, with no bookkeeping at all.
  5. Which deps? [value, delay] — a keystroke changes value, so cleanup → new timer. A pause longer than delay is the only way a timer survives to fire.
  6. Debouncing alone is still not safe for fetching. Two requests can be in flight at once and come back out of order, so a stale response overwrites a fresh one. The fix is the same mechanism again: abort the old request in the cleanup.

The code

function useDebounce(value, delay = 300) {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id);   // the whole trick
  }, [value, delay]);

  return debounced;
}

Used, with the race condition handled:

const [query, setQuery] = useState('');
const debouncedQuery = useDebounce(query, 400);

useEffect(() => {
  if (!debouncedQuery) return;
  const ctrl = new AbortController();

  fetch(`/api/search?q=${debouncedQuery}`, { signal: ctrl.signal })
    .then(r => r.json())
    .then(setResults)
    .catch(e => { if (e.name !== 'AbortError') setError(e); });

  return () => ctrl.abort();   // a stale request cannot overwrite fresh results
}, [debouncedQuery]);

The cleanup checklist

Four things always need one:

  1. Timers — clearTimeout / clearInterval
  2. Listeners and subscriptions — removeEventListener, unsubscribe
  3. In-flight requests — AbortController
  4. External instances — ws.close(), observer.disconnect(), worker.terminate()

Without them: memory leaks, state set after unmount, duplicated subscriptions. StrictMode in dev mounts, unmounts and remounts every component on purpose to expose exactly this — if your effect misbehaves under StrictMode, your cleanup is wrong.

29. React.memo vs useMemo

Analogy: same idea at two different sizes. useMemo is keeping one ingredient you already chopped. React.memo is keeping the whole finished dish and not cooking it again because the order has not changed. And the catch that trips everyone: if you hand the kitchen a freshly written order ticket every time — even with identical contents — they will cook it again. That is what an inline function prop does to React.memo.

Why either exists. React's default behaviour is to redo work rather than track what changed: when a component re-renders, React calls the function again from the top — recomputing every value inside it — and re-renders all of its children, whether or not anything those children depend on actually changed. That default is deliberate and usually fine, because calling a function and diffing a small tree is cheap. Memoization is the opt-out for when it isn't: you tell React "if these inputs are unchanged, reuse last time's result instead of doing the work again."

Both APIs apply that one idea, at different scopes — and that is the whole distinction.

Different levels of the same idea. React.memo memoizes a component's rendered output. useMemo memoizes a value inside a render.

30. How React renders UI changes

Analogy: you do not rearrange a room by shoving furniture around while people watch. You sketch the new arrangement (render — cheap, on paper, throw it away if you change your mind), compare it to the room as it is (diff), and then make one trip with a short list (commit — the only part anyone sees).

The real question: what happens between you calling setState and a pixel changing on the screen? The thing to understand first is that you never update the UI in React. You describe what the UI should look like for the current state, and React works out the smallest set of DOM operations that turn what is on screen now into what you described. That indirection is the whole design — it is why you write declarative code, and it is what lets React interrupt, reorder or throw away work without you knowing.

It does this in three phases, and the separation between them matters more than the names.

Three phases. Name them in order — this is the backbone answer.

  1. Trigger — setState (or a parent render) marks the component dirty and schedules work. Updates in the same tick are batched into one render.
  2. Render (pure) — React calls your function. It returns a new tree of React elements — plain objects, no DOM touched. React diffs that tree against the previous one (reconciliation, §19) and builds a list of mutations. This phase is interruptible in concurrent React: it can be paused, abandoned, or restarted, which is exactly why render must have no side effects.
  3. Commit (synchronous) — React applies the mutation list to the real DOM in one pass (appendChild, attribute writes, text updates), then runs refs and layout effects, paints, then runs passive effects.
setCount(1)  →  schedule  →  render (diff, no DOM)  →  commit (DOM writes)
                                                        ├─ useLayoutEffect  (before paint, blocking)
                                                        ├─ browser paints
                                                        └─ useEffect        (after paint, async)
The key sentence: "Rendering in React does not mean touching the DOM. Rendering means calling the component to produce a description of the UI. Only the commit phase writes to the DOM — and React writes only the differences it found, not the whole tree."

The diffing rules that decide what survives: different element type at the same position → tear down the subtree and rebuild it; same type → keep the DOM node, patch the changed attributes; lists are matched by key, which is why index-as-key corrupts state when the list reorders. See §18 (Virtual DOM) and §19 (Fiber) for the deep version.

31. useLayoutEffect

Analogy: the stage is set but the curtain has not gone up yet. useLayoutEffect is your last chance to walk out and move a chair while the audience still cannot see. useEffect runs after the curtain rises — so if you move the chair there, everyone watched it jump.

What it is. A hook for running code after React has updated the DOM but before the user can see the result. It is the same hook as useEffect in every visible way — same signature, same dependency array, same cleanup contract. The only thing that differs is when React chooses to run your callback, and that single difference is the entire reason it exists.

The problem it solves. Some code has to read the DOM before it can decide what the UI should look like. How tall is this tooltip? Did this menu overflow the bottom of the window? How wide is this text? None of those have an answer until the element actually exists in the document — but the moment it exists, the browser is free to paint it, and the user sees it in whatever position you guessed before you had the measurement. You measure, you correct, and the correction arrives one frame late. The visible result is a flicker: the element appears in the wrong place, then jumps.

How it solves it. React runs layout effects inside the commit phase, synchronously, while the browser is still blocked from painting. If you call setState in there, React re-renders and re-commits immediately, still before paint. So the intermediate, wrong-looking state never reaches the screen — the user only ever sees the corrected frame. useEffect, by contrast, is deliberately deferred until after paint, precisely so that ordinary side effects (fetching, logging, subscribing) cannot delay showing the UI.

commit DOM changes
  ├─ useLayoutEffect runs   ← synchronous, browser is blocked, you can still fix things
  ├─ browser paints         ← the first thing the user actually sees
  └─ useEffect runs         ← asynchronous, too late to change this frame invisibly

So the rule is: if the effect changes something the user would otherwise see wrong for one frame, it is a layout effect. If it does not affect what is on screen right now, it is a normal effect.

function Tooltip({ anchor, children }) {
  const ref = useRef(null);
  const [pos, setPos] = useState({ top: 0, left: 0 });

  useLayoutEffect(() => {
    const a = anchor.getBoundingClientRect();
    const t = ref.current.getBoundingClientRect();
    setPos({ top: a.top - t.height, left: a.left });   // measured and corrected BEFORE paint
  }, [anchor]);

  return <div ref={ref} style={{ position: 'fixed', ...pos }}>{children}</div>;
}

Use it only for: measure-then-mutate. Reading getBoundingClientRect/scrollHeight and immediately repositioning — tooltips, popovers, autosizing textareas, restoring scroll position, measuring text to truncate it. With useEffect the user sees one frame in the wrong place, then a jump: visible flicker.

The tradeoff to volunteer: "It blocks paint. The browser cannot show anything until my callback returns, so slow work here is directly janky frames. It is the exception; useEffect is the default — data fetching, subscriptions, logging, timers. And it does not run during SSR, so it warns on the server — guard it or move the logic."

Related: useInsertionEffect (earlier still, for CSS-in-JS injecting styles) and ResizeObserver, which is often the better answer than measuring in an effect on every render.

32. Controlled vs uncontrolled inputs

Analogy: who holds the pen? Controlled = you are reading over the user's shoulder and writing every letter into your own notebook as they type; the notebook is the truth, the paper just mirrors it. Uncontrolled = you let them fill in the form and only read it when they hand it back at the end.

The underlying problem. A form input in the browser already holds state of its own: the DOM node remembers what the user typed, with no help from React. So putting React in front of a form creates a duplicate — two places that both think they know the current value. Something has to decide which one is the truth, and the two possible answers are exactly these two patterns.

Who owns the value? React state → controlled. The DOM node → uncontrolled.

// Uncontrolled — the DOM keeps the value, you read it when you need it

33. Custom hook restrictions

Analogy for the rule everyone breaks: React stores your hooks in numbered lockers, assigned by the order you asked for them — not by name. First useState gets locker 1, the next gets locker 2, and so on. Skip one behind an if and every later hook shifts down a locker, so your useEffect opens the state locker and finds somebody else's socks. That is the whole reason for "always call hooks at the top level."

What a custom hook is for. It is how you take stateful logic out of a component so other components can reuse it — the thing plain functions could never do, because state, effects and lifecycle were locked inside component classes. A custom hook has no special syntax and no React API behind it: it is an ordinary function that happens to call hooks. That is also why it comes with restrictions — it inherits every rule the hooks inside it have, and it has no way to opt out of them.

A custom hook is just a function that calls other hooks — so it inherits the Rules of Hooks exactly.

  1. Name must start with use. Not cosmetic — it is how the linter and React DevTools know to apply the rules.
  2. Call hooks only at the top level. No hooks inside conditions, loops, nested functions, try/catch or after an early return. React identifies hooks by call order, not by name — a skipped hook shifts every later hook onto the wrong state slot.
  3. Call hooks only from React functions — a component or another custom hook. Not from plain utilities, event handlers, class components or module scope.
  4. No shared state between callers. Each call site gets its own independent state. Two components calling useCounter() do not share a counter — if you need that, you need context or an external store (§36).
  5. It must be callable unconditionally by its consumer, which means a custom hook cannot decide at runtime "I will not use state this time."
// WRONG — conditional hook call
function useThing(id) {
  if (!id) return null;          // early return before the hook
  const [data, setData] = useState(null);
}

// RIGHT — hook always runs, the condition moves inside it
function useThing(id) {
  const [data, setData] = useState(null);
  useEffect(() => { if (!id) return; fetchIt(id).then(setData); }, [id]);
  return data;
}
Why the rule exists — the mechanism, not the mantra: "Hooks are stored as a linked list on the fiber, and on every render React walks that list in order. There is no key, just position. So conditionally calling a hook misaligns the list and you get another hook's state — hence 'rendered fewer hooks than expected'."

Not restrictions, but worth adding: a custom hook should return a stable shape (array for positional like useState, object for named), and eslint-plugin-react-hooks enforces all of the above — say you have it on as an error, not a warning.

34. How to optimize performance in a React app

Analogy: "the app is slow" is like "the car is making a noise." It could be too much luggage (bundle size), driving in circles (re-rendering more than needed), or the engine struggling (expensive work per render). Three different problems, three different mechanics. Diagnosing before you open the bonnet is the entire answer.

Reframe the question first. "The app is slow" is not one problem, it is three, and conflating them is the most common weak answer. An app can be slow because it ships too much JavaScript before it can do anything; because it re-renders far more of the tree than the change justified; or because each individual render or paint does expensive work. Those have different causes, different fixes, and different tools for finding them. So the first move is always to measure and find out which one you actually have (§24) — then work the matching bucket.

Answer in three buckets, and lead with "measure first — §24" so you do not sound like someone who memoized everything.

1. Ship less JavaScript (usually the biggest win, and it is not a React problem)

  • Route-level code splitting — React.lazy + Suspense, dynamic import() (§23)
  • Audit the bundle — source-map-explorer; swap heavyweights (moment → date-fns/Temporal, lodash → single imports)
  • Tree shaking, modern build target, compression; move work server-side with SSR/RSC (§21)

2. Render less

  • Keep state local and as low in the tree as possible — the cheapest fix is a smaller re-render scope, not memoization
  • React.memo + useMemo/useCallback for stable props on expensive subtrees (§29)
  • Lift content up / push state down: pass expensive subtrees as children so they are not recreated by the stateful parent
  • Split bloated context providers — a context value change re-renders every consumer
  • Virtualize long lists (§35)
  • useTransition / useDeferredValue to keep typing responsive while a heavy list filters
  • Debounce/throttle high-frequency handlers (§26)

3. Make each render and each paint cheaper

  • Stable keys, never the array index on reorderable lists
  • Images: correct dimensions, loading="lazy", modern formats, next/image
  • Avoid layout thrash — batch reads then writes; prefer transform/opacity animations (compositor-only)
  • Offload genuinely heavy computation to a Web Worker (§11)
  • Cache server state properly — TanStack Query/SWR dedupe and cache requests, which removes renders you never needed
Close with the honest framing: "Most 'React is slow' reports are not React. They are a 2MB bundle, an unoptimized image, or a waterfall of requests. So I start with a Lighthouse and a React Profiler trace, fix the biggest number, and only then reach for memoization — which has its own cost and makes code harder to read."

35. 1,000 rows without hurting performance → virtualization

Analogy: a spreadsheet with 100,000 rows does not hurt your computer, because the screen only ever holds about 30 of them and the scrollbar is a lie about how much is below. That is exactly the trick: keep roughly the rows you can see, plus a spacer tall enough to make the scrollbar honest.

Why this hurts in the first place, and it is not React. Every DOM node the browser keeps around costs memory, style recalculation, and a slot in layout. 1,000 rows means the browser computes styles and geometry for thousands of boxes on first paint and again whenever anything shifts — plus React now has 1,000 components to diff on every update. The user can see maybe 20 of them. You are paying for 980 rows nobody is looking at.

The idea behind the fix: stop creating what cannot be seen.

Answer: virtualization (windowing). Render only the ~20 rows in the viewport plus a small overscan buffer; as the user scrolls, reuse those nodes and change their content and offset. 1,000 rows, ~25 DOM nodes.

import { useVirtualizer } from '@tanstack/react-virtual';

function Rows({ items }) {
  const parentRef = useRef(null);
  const v = useVirtualizer({
    count: items.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 40,
    overscan: 5,
  });

  return (
    <div ref={parentRef} style={{ height: 600, overflow: 'auto' }}>
      <div style={{ height: v.getTotalSize(), position: 'relative' }}>
        {v.getVirtualItems().map(row => (
          <div key={row.key} style={{ position: 'absolute', top: 0, transform: `translateY(${row.start}px)`, height: row.size }}>
            {items[row.index].label}
          </div>
        ))}
      </div>
    </div>
  );
}
Why the naive version hurts: "1,000 rows is not a React problem, it is a DOM problem. Every node costs memory, style recalculation and layout, so the first paint is slow and every scroll frame has to lay out thousands of boxes. The fix is to stop creating nodes nobody can see — the spacer div keeps the scrollbar honest while only the visible window exists."

The outer wrapper has a fixed height and its own scroll container — that is mandatory, the virtualizer needs a measurable viewport. Variable row heights need measureElement (dynamic measurement), which is the follow-up question.

Name the alternatives and when each wins: pagination or infinite scroll (do not fetch 1,000 rows at all — usually the real answer); content-visibility: auto in CSS as a zero-dependency partial win; IntersectionObserver for simple lazy loading. Libraries: @tanstack/react-virtual, react-window, react-virtuoso, or AG Grid if it is a real data grid.

Trade-offs to mention unprompted: Ctrl+F stops finding off-screen rows, accessibility needs care (aria-rowcount, focus management), print and "select all" break, and SEO sees only the window — if the content must be indexable, paginate instead.

36. Why do we need external state management?

Analogy: prop drilling is passing a note through six people who do not care what it says just to reach the person at the end — and every one of them has to be told the note exists, so changing it means bothering all six. An external store is a whiteboard in the hallway: whoever needs the number walks over and reads it, and nobody in between is involved.

What "external" means here. A state manager is simply a place to keep state that lives outside the component tree, with components subscribing to the parts they care about. Normally React state lives in the tree — it belongs to one component, and the only way to share it is to move it up to a common ancestor and pass it down. That mechanism is what eventually breaks, and the breakage has a name.

The problem it removes is prop drilling. Without it, state lives in the nearest common ancestor and gets threaded down through every intermediate component — components that neither read nor care about that data, but must accept and forward it. Change the shape and you touch ten files.

// prop drilling
<App user={user}> → <Layout user={user}> → <Header user={user}> → <Avatar user={user} />
//                   ^ neither Layout nor Header uses `user`

What external state buys you beyond that: shared state across sibling branches (two distant components on the same data), state that outlives a component (unmount the page, keep the cart), one place to put complex update logic, and debuggability — DevTools, action logs, time-travel, replayable bug reports.

The honest version — what it does NOT solve: "A global store does not make re-renders free: a careless selector re-renders half the app on any store change. It does not solve server state — caching, deduping, revalidation, out-of-order responses — that is TanStack Query's job, not Redux's. It does not remove the need for local state; a form input in a global store is a mistake. And it does not reduce complexity, it relocates it: more indirection, more boilerplate, a harder first day for a new hire."

The escalation ladder to recite: local useState → lift it up → children/composition → Context (low-frequency, app-wide: theme, auth, locale) → external store (Zustand/Redux Toolkit/Jotai) for high-frequency or large shared state → and a server-state library for anything that came from an API. "Context fixes prop drilling but is not a performance tool — every consumer re-renders when the value changes; that is precisely when I move to a store with selectors."

37. The three principles of Redux

Analogy: Redux is a bank ledger. You never reach in and edit the balance; you write down a transaction ("deposited 50"), and the balance is whatever you get from replaying the transactions. Annoying compared to just changing the number — and it is the reason you can always answer "how did it get to this amount?", and the reason the bank can rewind.

What Redux is, before the principles. A predictable state container: one object holding your app state, changed only by dispatching plain description-objects through pure functions. Every constraint it imposes buys one property — you can always answer "how did the state get into this shape?" by replaying a list of actions. The three principles are those constraints, and each trades away some freedom for debuggability.

  1. Single source of truth — the whole app state lives in one store, one object tree. Easier to debug, serialize, persist and hydrate (SSR), and no two copies to drift apart.
  2. State is read-only — you never mutate it. The only way to change it is to dispatch an action, a plain object describing what happened. Every change funnels through one choke point, so it can be logged and replayed.
  3. Changes are made with pure functions — reducers: (state, action) => newState. No mutation, no API calls, no Date.now(), no randomness. Same inputs, same output, every time.
// reducer: pure, returns a NEW object
function todos(state = [], action) {
  switch (action.type) {
    case 'todos/added':   return [...state, action.payload];
    case 'todos/toggled': return state.map(t => t.id === action.payload ? { ...t, done: !t.done } : t);
    default:              return state;
  }
}
Why purity is the one that matters: "Purity is what makes time-travel debugging possible — replay the same action list over the same initial state and you land in exactly the same UI. It is also what makes React's reference-equality check work: a new object means a new reference means a re-render; mutating in place silently renders nothing."

The modern footnote: "Redux Toolkit is the standard today — createSlice lets me write state.push(x), but that is Immer recording my mutations on a draft proxy and producing a new immutable object. The reducer stays pure; the ergonomics just improved. Side effects live outside reducers, in thunks or middleware."

38. Presentational vs container components

Analogy: a blank form template versus the clerk who fills it in. The template knows nothing about where the data comes from, so you can reuse it or photocopy it for a demo. The clerk knows the filing system, the API, the store. The test tells you which half you are holding: if you would change it because the design changed it is the template; if you would change it because the data source changed it is the clerk.

What the pattern is. Splitting one component into two, divided by the reason you would edit it. If you would change it because the design changed, that is presentational. If you would change it because the data source or business rule changed, that is container. It is separation of concerns applied at the component level, and its real payoff is that the presentational half becomes trivially reusable and trivially testable — no mocks, no providers, props in and markup out.

The one-line map of all six. Array = a numbered queue. Object = a form with printed labels (labels must be words). 40. What is a Set?

A Set is just a list that refuses duplicates. Picture a plain array — same thing, one extra rule: the same value can never go in twice. You have ["a", "b", "c"] and you try to add another "b"? Nothing happens. A "b" is already in there, so the Set silently ignores you. That is the entire concept.

Which means you use a Set whenever you want a guarantee that there is no duplicate data — a list of tags, selected ids, email addresses, nodes you have already visited. You never have to check first; the Set keeps itself clean.

The second reason to use one: asking "is X in here?" is instant. With an array you have to walk it — arr.includes(x) checks every element until it finds a match, so a list of 10,000 items can mean 10,000 comparisons. A Set answers in one step, no matter how big it is. Put arr.includes() inside a loop and you have an O(n²) function; swap in set.has() and it is O(n).

Beyond those two things it behaves like an array you would expect: it keeps insertion order, it is iterable, and it holds values of any type.

A concrete one. Think of the contacts app on your phone. You import a SIM card, then a Google account, then a CSV your colleague emailed you — and now "Maria" is in there four times. That is an array: it took everything it was handed. If the phone number were the key of a Set, the second, third and fourth Maria would simply never have been added. (Hopefully one day my phone book will be fixed.)

const numbers = ["+55 11 90000", "+55 11 91111", "+55 11 90000"];

numbers.length;              // 3 — Maria is in here twice
new Set(numbers).size;       // 2 — the duplicate never made it in

So should you avoid arrays and use Sets everywhere? Absolutely not. A Set is important when you need to ensure there is no duplicate data. When you do not have that need, an array is often preferable: it is cheaper per element, you get index access (arr[0], which a Set has no concept of), you get the whole map/filter/reduce/sort/slice toolkit, and it survives JSON.stringify (a Set serializes to {} — a classic bug). You have to analyze the needs of your own application and decide which structure is the better fit.

One nuance, if someone pushes on it. In the classic textbook version, a set is backed by an array, so every insertion has to scan the whole thing for a duplicate first — O(n) to add, versus O(1) for a plain push. JavaScript's Set is hash-backed, so add is O(1) and that particular penalty does not apply. The lesson still does: uniqueness is never free, it is just paid in memory and overhead here instead of time.

const s = new Set([1, 2, 2, 3]);   // Set(3) {1, 2, 3}

s.add(4);         // chainable, returns the Set
s.has(2);         // true  — O(1), vs O(n) for arr.includes
s.delete(2);      // true if it was there
s.size;           // 3     — property, not a method
s.clear();

const unique = [...new Set(arr)];                  // the idiom everybody knows
const unique = Array.from(new Set(arr));

for (const v of s) {}                              // iterable
s.forEach(v => {});                                // (value, value, set) — key === value

How does it decide two values are "the same"? Basically ===, with one fix: NaN counts as equal to itself, so a Set can only ever hold one NaN. (The spec name for this rule is SameValueZero.) The trap question is objects: they are compared by identity, not by content, so two objects that look identical are still two different values — new Set([{a:1},{a:1}]).size === 2.

ES2025 added set methods — union, intersection, difference, symmetricDifference, isSubsetOf, isSupersetOf, isDisjointFrom. Mentioning them is cheap currency.

When I reach for it: deduping, "have I visited this node" in a graph walk, tracking selected ids, tag/permission membership — anywhere I would otherwise write arr.includes() inside a loop and make it O(n²).

41. What is a Map?

Analogy — the cloakroom at a theatre. You hand over your coat and you get a numbered ticket. When you come back, the attendant does not walk down the rail looking at every coat until they spot yours — they read the number and go straight to hook 47. Your ticket is the key, your coat is the value, and the whole point of the system is that finding your coat takes the same time whether there are 10 coats or 10,000. A Map is that cloakroom.

The problem it solves — start here, because this is the actual purpose. Say you have 5,000 users and a user id, and you need that user's name. With an array you have to look:

// the slow way: walk the shelf until you spot it
const user = users.find(u => u.id === 4211);   // checks up to 5,000 items

Do that once and nobody notices. Do it inside a loop over 5,000 orders and you have just done 25 million comparisons for something that should have been instant. A Map removes the searching entirely: you built the ticket system up front, so now you just read the ticket number.

// the fast way: build the cloakroom once...
const byId = new Map(users.map(u => [u.id, u]));   // key = id, value = the user

// ...then every lookup after that is one step, no searching
byId.get(4211);     // the user, instantly — same speed with 10 users or 10 million

That is the purpose in one sentence: a Map is a thing you put stuff into under a label of your choosing, so you can get it back later by that label without ever searching for it. Everything else about Map is a detail hanging off that.

So why not just use an object? You can! { 4211: user } does roughly this too, and for simple cases people do exactly that. But an object has one hard limit: the labels on an object can only be text. Write obj[4211] and JavaScript quietly turns the number 4211 into the string "4211" behind your back. Try to use something bigger than text as a label — an actual object, a function, a button on the page — and the object mashes it into useless text:

const obj = {};
obj[document.body] = 'hello';
Object.keys(obj);        // ["[object HTMLBodyElement]"]  ← the button is gone, it's just text now
                         // every element you store collides into that SAME one key

const m = new Map();
m.set(document.body, 'hello');
m.get(document.body);    // 'hello'  ← the real element is the key, not a description of it

That is the one real difference, and it is why Map exists: an object's label has to be a word; a Map's label can be the thing itself. "Remember that this exact button has been clicked 3 times" is a Map job and an object simply cannot do it.

The whole API — it is five methods and one property:

const m = new Map();                 // or new Map([['a', 1], ['b', 2]]) to start it filled

m.set('a', 1);        // put 1 on the hook labelled 'a'  (returns the map, so it chains)
m.get('a');           // 1        — undefined if that label was never used
m.has('a');           // true     — "is there anything on this hook?"
m.delete('a');        // true if something was there
m.size;               // 2        — a plain property, no counting needed
m.clear();            // empty the cloakroom

for (const [key, value] of m) { }    // walk it in the order things were added
m.keys(); m.values(); m.entries();   // the three views

Object.fromEntries(m);               // Map → plain object (only if the keys are strings)
new Map(Object.entries(obj));        // plain object → Map

Two small things that get asked. Keys are compared the way === compares, with one fix: NaN matches itself, so a Map can hold only one NaN key. And objects are compared by identity, not by looks — m.set({id:1}, 'x').get({id:1}) gives undefined, because those are two different objects that merely resemble each other. Same rule as Set (§40).

When I reach for it: any id → record index I am about to look up repeatedly; counting occurrences (counts.set(w, (counts.get(w) ?? 0) + 1)); attaching data to DOM nodes or component instances; and any cache whose keys arrive at runtime from outside. If I am about to write .find() inside a loop, I build a Map instead.

42. Map vs Object

One line: an Object is a form with field labels printed on it — a known, fixed shape you fill in: name, email, age. A Map is an empty filing cabinet — you add and pull drawers all day and you never knew in advance what the labels would be. Object for a record, Map for a lookup table.

They look like the same tool because both store key → value. The difference is what each one was built for. An object's keys are part of your source code — you typed them, you know them, you read them back with a dot. A Map's keys are data — they arrive at runtime, from a server, from user input, from the DOM, and you never type them literally anywhere.

Map for a hash map — keys added and removed at runtime, non-string keys, or when I need size and ordered iteration. The practical clincher is prototype collisions: a user-supplied key called __proto__ in a plain object is a real vulnerability class, and in a Map it is just a key. If I must use an object for a dynamic dictionary, I reach for Object.create(null) (§46)."

43. WeakMap — and why we need it

Analogy — the lost property office vs. a sticky note. A normal Map is the lost property office: once an umbrella is logged in there, it stays in the building forever, because the office is still holding it. Nobody can ever throw it out — there is a record. A WeakMap is a sticky note stuck to the umbrella itself: the note travels with the umbrella, and the day the umbrella gets thrown away, the note goes in the bin with it. You remembered something about the umbrella without becoming the reason it can never be thrown away.

First, the thing nobody explains: JavaScript cleans up after you. You never free memory by hand. Instead the engine runs a garbage collector, and its rule is simple:

If nothing in your program can still reach an object, it is garbage and the engine is free to delete it. If anything at all can still reach it — one variable, one array slot, one map entry — it stays in memory.
let node = document.createElement('div');   // something points at it → it lives
node = null;                                // nothing points at it → the engine can delete it

So "a memory leak in JavaScript" is never "I forgot to free it". It is always something is still pointing at a thing you are finished with, and that something is very often a cache you wrote yourself.

Now the actual problem. You want to remember some data about each row in a table — its measured height, say — so you cache it keyed by the element:

const cache = new Map();                 // ← a normal Map

function getHeight(row) {
  if (!cache.has(row)) cache.set(row, row.getBoundingClientRect().height);
  return cache.get(row);
}

This works perfectly and it is also a slow memory leak. Follow the rows:

// user scrolls; the app removes row 1 from the page and forgets about it
row.remove();
row = null;                  // you dropped your reference...
                             // ...but `cache` still has that element as a key.
                             // The engine sees something pointing at it → it must keep it.
                             // The element, its children, its event listeners: all still in memory.

Nothing in your app can reach that row any more, nothing will ever call getHeight on it again, and it is still there. Scroll a long list for ten minutes and your cache is now a museum of thousands of dead DOM nodes. The cache stopped being a cache and became the thing keeping the garbage alive. That is a real bug with a real symptom: it is the classic "why does this dashboard use 2GB after an hour".

The fix is one word. Same API, same code, different collection:

const cache = new WeakMap();             // ← the only change

function getHeight(row) {
  if (!cache.has(row)) cache.set(row, row.getBoundingClientRect().height);
  return cache.get(row);
}
// row.remove(); row = null;  →  nothing else points at it, so the engine deletes
// the element AND the cache entry disappears with it. No leak, no cleanup code.

A WeakMap holds its keys weakly, which means exactly this: the engine does not count a WeakMap entry as a reason to keep something alive. If the WeakMap is the last thing pointing at a key, the key gets collected and the entry vanishes on its own.

Why it looks so crippled — and why that is the point. Every missing feature follows from one fact: you cannot predict when the garbage collector runs.

RestrictionWhy it has to be that way
No size, no keys(), no iteration, no clear()The contents shrink by themselves at a moment you cannot predict. If size existed it would return a different number depending on whether the collector happened to run — your program's behaviour would depend on engine timing. So it is simply not exposed.
Keys must be objects (or Symbols) — not strings or numbersWeakness only means anything for a thing with identity that can go away. The string 'hello' is not an item sitting somewhere waiting to be thrown out — there is nothing to collect, so a weak reference to it would be meaningless.
Not serializable, not really inspectableSame reason: there is no stable snapshot to take.

Methods, and that is the whole surface: get / set / has / delete. Note there is no constructor shortcut worth much — new WeakMap([[obj, 1]]) works, but you almost always start empty and fill it as objects arrive.

Why we need it, out loud: "A WeakMap lets me attach data to an object without owning its lifetime. A normal Map holds its keys strongly, so using one as a cache keyed by DOM nodes or component instances is a textbook memory leak — the map keeps every object alive long after the app is done with it. A WeakMap makes the cache follow the object's life instead of extending it: when the object goes, the entry goes. The cost is that I give up size and iteration, and that is deliberate — the contents change at GC time, which I cannot observe without making my program depend on when the collector ran."

Where it actually shows up: metadata and caches keyed by DOM nodes or component instances; private fields before #private existed (const _secrets = new WeakMap() — the data is unreachable without the instance and the module-scoped map); memoizing a function on object identity; cycle detection in a deep clone (§47). React and Immer both use them internally. If you need weakness for a single object rather than a collection, that is WeakRef / FinalizationRegistry (§39).

44. WeakSet — and how it differs from WeakMap

Where the line is: a WeakMap remembers something about an object — "this row is 42px tall". A WeakSet remembers only that you have seen an object — "I already dealt with this one". It is the same split as Map vs Set (§42): key→value versus bare membership. If the thing you need back is a piece of data, WeakMap. If it is a yes/no, WeakSet.

What it is. A group of objects you can add to and ask about, holding its members weakly — so being in the set is not a reason for an object to stay in memory. Three methods, and that is everything:

const ws = new WeakSet();

ws.add(obj);        // put it in the group   (chainable)
ws.has(obj);        // true / false — the only question a WeakSet can answer
ws.delete(obj);     // true if it was in there

// no size, no iteration, no clear, objects only — same reasons as WeakMap (§43)

The problem it solves: a boolean flag that must not pin the object. You want to wire up each widget exactly once. The obvious move is a flag on the object itself, which is fine until you do not own the object or must not mutate it — so you track it outside:

const initialised = new Set();            // ← a normal Set: the leak

function setup(widget) {
  if (initialised.has(widget)) return;    // already done, skip
  initialised.add(widget);
  // ...expensive one-time wiring
}

That Set now holds every widget the app has ever created, forever — and each entry exists purely to record a single true. You are keeping a whole object alive to remember one bit. Swap the collection and the problem is gone:

const initialised = new WeakSet();        // ← the only change
// widget destroyed → it drops out of the set by itself, flag and all.

The other classic: cycle detection. Walking a structure that might point back at itself, you need "have I been here before?" — and you must not keep the visited objects alive after the walk:

function hasCycle(obj, seen = new WeakSet()) {
  if (obj === null || typeof obj !== 'object') return false;
  if (seen.has(obj)) return true;                  // been here → cycle
  seen.add(obj);
  return Object.values(obj).some(v => hasCycle(v, seen));
}

Note the sibling case: a deep clone uses a WeakMap instead, because it needs "which copy did I already make of this?" — a piece of data, not a yes/no (§47). That pair is the clearest illustration of the line between the two.

One line: "WeakSet is membership without ownership — 'have I already handled this object?' answered without being the reason it stays in memory. Reach for it for one-time-setup flags, validation marks, and visited-sets during a traversal. The moment I need to store a value against the object rather than a flag, it is a WeakMap."

45. Promise methods for multiple parallel requests

Analogy — you send three friends out to pick things up. They all leave at the same time no matter which method you pick; the only question is what you do when one of them fails. all: if anybody fails, the evening is off. allSettled: tell me how each of you did, we work with what we got. race: whoever gets back first, good or bad news, that is what we go with. any: first one with good news wins; I only care if all three strike out.

What they are for. When several requests do not depend on each other, doing them one after another wastes time equal to the sum of their latencies instead of the slowest one. These four static methods all take a list of promises and return a single promise that represents the whole group. They all start everything at once; the only thing that differs is what you want to happen when some of them fail — and that is how you choose between them.

Four combinators. All four take an iterable and start everything concurrently — the difference is only in when they settle and with what.

MethodResolves whenRejects whenResult
Promise.allall fulfilfirst rejection (fail fast)array of values, input order
Promise.allSettledall settlenever{status,value} / {status,reason} per item
Promise.racefirst to settleif that first one rejectedthat single outcome
Promise.anyfirst to fulfilonly if all reject → AggregateErrorfirst success
// all — I need everything, and partial data is useless
const [user, posts] = await Promise.all([getUser(id), getPosts(id)]);

// allSettled — dashboard: render what worked, show an error card for what didn't
const results = await Promise.allSettled([getUser(id), getPosts(id), getAds()]);
const ok = results.filter(r => r.status === 'fulfilled').map(r => r.value);

// race — timeout pattern
await Promise.race([fetch(url), new Promise((_, rej) => setTimeout(() => rej(new Error('timeout')), 5000))]);

// any — first mirror that answers wins
await Promise.any([fetch(cdn1), fetch(cdn2), fetch(cdn3)]);
The sentence that shows you understand parallelism: "Parallelism comes from starting the promises, not from the combinator. await a(); await b(); is sequential — b does not start until a resolves. Promise.all([a(), b()]) is concurrent because both functions were already called when the array was built. And 'parallel' is loose here: it is concurrent I/O on one thread, not parallel computation — that needs Web Workers (§11)."

Follow-ups to be ready for: Promise.all fails fast but the other requests keep running — it does not cancel them; cancellation needs AbortController (and AbortSignal.any/timeout). Rejections from the losers become unhandled unless caught. For 500 requests, do not fire them all — chunk them or use a concurrency limit (p-limit), or the browser's 6-per-host queue and the server both suffer.

46. How do we create an object in JS?

Analogy: an object literal is writing one thing by hand. A class or constructor is a cookie cutter — stamp out a hundred, and they all share one recipe card (the prototype) rather than each carrying a copy of it. A factory function is a person at a workbench handing you a finished item: no cutter, no recipe card, and whatever they keep on the bench stays private. Object.create(null) is a blank sheet with no recipe card at all — which is exactly what you want when the keys come from a stranger.

Why there is more than one way. All of these produce an object, so the question is never "which one makes an object" but what ends up on the prototype and how the methods are shared. A literal gives you a one-off. Constructors and classes give you many instances sharing one set of methods through the prototype chain. Factories give you instances whose "methods" are closures, with no this involved at all. Object.create lets you set the prototype explicitly — including to nothing.

// 1. Object literal — 95% of real code
const o = { a: 1, greet() { return this.a; } };

// 2. Constructor function + new   (pre-ES6 classes)
function User(name) { this.name = name; }
User.prototype.hi = function () { return `hi ${this.name}`; };
const u = new User('Ada');

// 3. class — same prototype mechanics, better syntax
class Admin extends User { #secret = 1; hi() { return 'admin ' + super.hi(); } }

// 4. Object.create — explicit prototype control
const child  = Object.create(parentObj);        // parentObj becomes the prototype
const pureMap = Object.create(null);            // NO prototype: a safe dictionary

// 5. Factory function — closures instead of `this`, no `new` needed
const makeUser = name => ({ name, hi: () => `hi ${name}` });

// 6. new Object() / Object.assign / spread / structuredClone / Object.fromEntries / JSON.parse
const merged = { ...a, ...b };
const fromPairs = Object.fromEntries([['a', 1]]);

What new actually does — the four steps worth reciting: creates an empty object, sets its [[Prototype]] to the constructor's .prototype, calls the constructor with this bound to it, returns it unless the constructor returns another object.

Have an opinion: "Literals for data, class when I need inheritance or many instances with shared methods, factory functions as my default when I want encapsulation without this binding headaches, and Object.create(null) when the object is a lookup table built from user input — no prototype means no __proto__ or toString collisions."

47. Methods to copy an object (shallow and deep)

Why copying is a question at all. Objects are held by reference, so const b = a does not copy anything — both names point at the same object, and "changing b" changes what a sees too. Copying means producing a genuinely separate object, and the only real decision is how deep to go: just the top level (fast, but nested objects are still shared), or the whole structure (safe, but slower and full of edge cases).

See §14 for the mental model; this is the method list.

Shallow — one level only:

{ ...obj }                      // spread — the default; own enumerable props
Object.assign({}, obj)          // same, but mutates the target; triggers setters
Object.assign({}, a, b, c)      // merge, later wins
Object.fromEntries(Object.entries(obj))     // lets you filter/transform while copying
Object.create(Object.getPrototypeOf(obj), Object.getOwnPropertyDescriptors(obj))
                                // the only shallow copy that preserves getters,
                                // non-enumerables and the prototype
// arrays: [...arr], arr.slice(), Array.from(arr), arr.concat(), arr.toSpliced()/with()

Note what spread drops: the prototype, non-enumerable properties, and property descriptors — getters are invoked and flattened into plain values. That nuance is §48 territory and the reason the getOwnPropertyDescriptors form exists.

Deep — the approach question:

structuredClone(obj)            // ✅ native default. Handles nested objects, arrays,
                                //    Date, RegExp, Map, Set, ArrayBuffer, Blob,
                                //    and CIRCULAR references.
                                // ❌ throws on functions, DOM nodes, Symbols;
                                //    drops the prototype (class instance → plain object)
                                //    and property descriptors/getters

JSON.parse(JSON.stringify(obj)) // the legacy trick — know its five failures:
                                // drops undefined/functions/Symbols, Date → string,
                                // NaN/Infinity → null, throws on cycles, loses prototype

_.cloneDeep(obj)                // lodash — most tolerant, handles functions-by-reference
                                // and class prototypes; a dependency though

// hand-rolled, when asked to write one:
function deepClone(value, seen = new WeakMap()) {
  if (value === null || typeof value !== 'object') return value;   // primitives
  if (seen.has(value)) return seen.get(value);                     // cycles
  if (value instanceof Date) return new Date(value);
  if (value instanceof Map) { const m = new Map(); seen.set(value, m);
    for (const [k, v] of value) m.set(deepClone(k, seen), deepClone(v, seen)); return m; }
  const out = Array.isArray(value) ? [] : Object.create(Object.getPrototypeOf(value));
  seen.set(value, out);                                            // BEFORE recursing
  for (const k of Reflect.ownKeys(value)) out[k] = deepClone(value[k], seen);
  return out;
}
How to choose, out loud: "structuredClone unless I need functions or class prototypes preserved, in which case lodash. And in React the real answer is usually neither — I do a targeted copy of just the path I am changing, or use Immer. Deep-cloning whole state on every update is both slow and a sign the state shape is wrong."

The WeakMap for cycle tracking (§43) and setting it before recursing is the detail that separates a memorized answer from an understood one.

48. Object property descriptors

Analogy: a property is not a value, it is a file with permission bits on it. Can it be overwritten (writable)? Does it show up when someone lists the folder (enumerable)? Can it be deleted or have its own permissions changed (configurable)? obj.a = 1 just creates the file with all permissions open, which is why most people never find out the bits exist.

What they are. A property is not just a key pointing at a value. Internally, every property is a small record — a descriptor — holding the value plus metadata about what you are allowed to do with it: can it be reassigned, does it show up when the object is listed or copied, can it be deleted. obj.a = 1 hides all of that behind a sensible default.

Why it exists. "Key to value" is too narrow for everything an object needs to express. Read-only constants, internal fields that should not appear in Object.keys or JSON.stringify, computed properties that run a function when read, frozen configuration — all of those are the same mechanism with different flags. Descriptors are the API for reading and setting them, and they are what freeze, seal, class and Proxy are built on top of.

Every property is not just a value — it is a descriptor, an internal record with flags. There are two kinds.

Data descriptor: value, writable, enumerable, configurable.
Accessor descriptor: get, set, enumerable, configurable. (A property is one or the other, never both.)

Flagfalse means
writableassignment is ignored (throws in strict mode)
enumerablehidden from for…in, Object.keys, spread and JSON.stringify
configurablecannot be deleted or redefined — one-way door
const o = { a: 1 };

// { value: 1, writable: true, enumerable: true, configurable: true }  ← literal defaults

// flags DEFAULT TO FALSE when defined this way → read-only, hidden, locked

  enumerable: true,

The asymmetry worth naming: "Properties created by a literal or assignment get all three flags true. Properties created with defineProperty default to all false. That bites people constantly — you define a property and then wonder why it vanished from Object.keys and from your spread copy."

Where it actually shows up: class methods are non-enumerable by design (which is why for…in over an instance does not list them); Object.freeze for immutable config; getOwnPropertyDescriptors is the only correct way to copy getters (§47); and Reflect/Proxy traps are defined in terms of descriptors — the mechanism behind Vue's reactivity and Immer's drafts.

49. Generators — and what happens on yield

Analogy: a normal function is a vending machine that dumps the whole shelf at once — one press, everything falls out, done. A generator is a ticket dispenser: you press it, you get number 1, and it just sits there remembering it is on number 1 until somebody presses again. It can do that forever without ever holding a list of all the numbers.

What a generator is. An ordinary function has exactly two moments: you call it and it runs, then it returns and everything inside it is gone. A generator breaks that contract — it can stop partway through, hand a value back to the caller, and stay frozen in place until someone asks it to continue, with all of its local state still intact.

Why that is useful. It inverts who is in control. Normally the function decides how long it runs; with a generator the caller decides, pulling one value at a time. That makes it possible to describe a sequence without computing it — including an infinite one — and to compute only as much as the consumer actually consumes. It is the machinery behind custom iterables, lazy evaluation, and (under the hood) async/await.

A function* does not run when you call it. It returns a generator object — an iterator you pull values out of. yield pauses the function and hands a value out, keeping the entire execution context alive: local variables, the position in the loop, the call stack frame. The next .next() resumes exactly there.

function* idGen() {
  let id = 0;
  while (true) {
    const reset = yield ++id;        // pauses here, hands out ++id
    if (reset) id = 0;               // ...and `reset` is whatever next() is CALLED with
  }
}

const g = idGen();        // nothing has executed yet
g.next();                 // { value: 1, done: false }   ← runs up to the first yield
g.next();                 // { value: 2, done: false }
g.next(true);             // { value: 1, done: false }   ← argument becomes `reset`
g.return('stop');         // { value: 'stop', done: true }  — terminates it

The outcome of a yield, precisely: .next() returns { value, done }. value is the yielded expression, done is false while the function is merely paused. When the function finally returns, you get { value: returnValue, done: true }, and every call after that gives { value: undefined, done: true }. Inside the generator, the yield expression itself evaluates to the argument passed to the next next() — that two-way channel is the part people miss.

function* inner() { yield 'a'; yield 'b'; }
function* outer() { yield 1; yield* inner(); yield 2; }   // yield* delegates
[...outer()];                                            // [1, 'a', 'b', 2]

// lazy infinite sequence — no array is ever built
function* take(n, it) { for (const v of it) { if (n-- <= 0) return; yield v; } }
[...take(3, idGen())];                                   // [1, 2, 3]
The one-liner: "A generator is a function with a pause button. Normal functions run to completion and lose everything; a generator suspends mid-execution with its state intact and lets the caller decide when — and whether — to continue. That is lazy evaluation, and it is also exactly the machinery async/await is built on: await is a yield that the runtime resumes when a promise settles."

Real uses to name: infinite/lazy sequences and pagination (fetch page by page without loading everything); custom iterables ([Symbol.iterator]*); tree/graph traversal without building an array; redux-saga's effect model; for await…of over async function* for streaming responses. "In day-to-day product code I rarely write one — but async iterators over a streamed API response are the case where I do."

50. What is the console output order?

What does this snippet print, and in what order? Walk through it out loud as you go.

Plain version: the computer finishes everything already on its desk, then does the sticky notes, and only then picks up one parked job. Three piles, always in that order.

Work it out

  1. Draw three piles. Now (plain statements), sticky notes (promise reactions — microtasks), parked (timers — macrotasks).
  2. Walk the code top to bottom and ask one question per line: does this run now, or does it go on a pile?
  3. setTimeout → parked. Even at 0ms. It is a request, not a jump.
  4. new Promise(executor) → the executor runs now, immediately, before the next line. This is the trap the question is built around; most people expect it to be async.
  5. .then / .catch → these only register a handler. Nothing runs; a sticky note goes on the pile.
  6. When the last plain statement finishes, the desk is clear — so every sticky note is done, all of them, in order.
  7. Only then does one parked job get picked up. That is why a 0ms timer still loses to every promise.
console.log("start");

setTimeout(() => console.log("timeout"), 0);

new Promise((resolve, reject) => {
  console.log("promise constructor");
  reject();
})
  .then(() => console.log("promise then"))
  .catch(() => console.log("promise catch"))
  .then(() => console.log("promise second then"));

console.log("final");

The walk-through to say out loud:

  1. "start" — plain synchronous call.
  2. setTimeout — the callback is handed to the timer API, not run. It lands in the macrotask queue when the 0ms elapses.
  3. "promise constructor" — the executor runs synchronously, immediately, inside new Promise. This is the trap: people expect it to be async. It is not. reject() then settles the promise as rejected right away.
  4. .then().catch().then() — these only register handlers. Nothing runs yet; the reactions are queued as microtasks.
  5. "final" — last synchronous statement. The call stack is now empty.
  6. Microtask queue drains completely: the first .then() has no rejection handler, so the rejection passes straight through it — "promise then" never prints. .catch() catches it → "promise catch". A catch handler that returns normally produces a fulfilled promise, so the chain recovers and the last .then() fires → "promise second then".
  7. Only then does the event loop take a macrotask → "timeout".
The two sentences that win this question: "The Promise executor is synchronous — only the .then/.catch reactions are asynchronous. And the entire microtask queue is drained before a single macrotask runs, so every promise callback here finishes before setTimeout(…, 0) gets its turn — even though the timer was scheduled first."

Follow-ups to be ready for:

  • "Why doesn't promise then print?" — .then(onFulfilled) with one argument has no onRejected, so a rejected promise skips it and propagates down the chain to the nearest rejection handler. .then(f, g) would have caught it in g; .then(f).catch(g) also catches errors thrown inside f — that is the difference between the two forms.
  • "What if reject() became resolve()?" → start, promise constructor, final, promise then, promise second then, timeout — the .catch is skipped because nothing rejected.
  • "Remove the .catch?" → unhandled rejection warning, and "promise second then" never prints.
  • "Where does async/await fit?" — await is a microtask resumption; the code after an await behaves exactly like a .then callback. Related: §3 and §13.

51. Which console.log runs, on mount and on click?

Which console.log runs — on the first render, and then on a click?

Plain version: three effects, three different rules for "should I run again?". The first render is special: there is no previous render to compare with, so everything runs.

Work it out

  1. Mount is a freebie. No previous dependency array exists, so there is nothing to compare and every effect runs — in the order they are written, after the DOM is painted.
  2. For every later render, React asks one question per effect: is this dependency array the same as last time's?
  3. No array at all → nothing to compare → it runs every single time.
  4. [] → empty compared with empty → always equal → it never runs again.
  5. [value] → Object.is(0, 1) is false → it runs.
  6. Now answer the click: value changed, so the no-array one and the [value] one run, and the [] one does not.
export default function Lifecycle() {
  const [value, setValue] = useState(0);

  useEffect(() => {
    console.log("NO DEP");
  });

  useEffect(() => {
    console.log("EMPTY DEP");
  }, []);

  useEffect(() => {
    console.log("VALUE");
  }, [value]);

  return (
    <button onClick={() => { setValue((prev) => { return ++prev }) }}>{value}</button>
  );
}

Say the mechanism, not the table: "React stores the previous dependency array on the fiber and compares it element by element with Object.is. No array means nothing to compare, so it always runs. That is also why objects and arrays in deps are dangerous — a new reference every render compares unequal and silently turns a dependency-guarded effect back into a run-every-render effect."

The three things to volunteer before they ask:

  1. StrictMode in dev double-invokes effects — on mount you would actually see NO DEP, EMPTY DEP, VALUE, NO DEP, EMPTY DEP, VALUE. It mounts → unmounts → remounts deliberately to expose missing cleanup (§28). In production it logs once. Naming this unprompted is a strong signal.
  2. ++prev is a smell — it works here only because prev is a number and therefore a copy, but it reads as a mutation of the previous state. prev => prev + 1 is the correct idiom. (The updater form itself is right — see the stale-closure point in §2.)
  3. Bail-out: if an updater returns the same value, React may skip the re-render entirely, and then none of the effects run. Here each click increments, so it always re-renders.

Likely follow-up — "when exactly do these log relative to the paint?" After commit and after the browser paints; useLayoutEffect would log before paint, synchronously (§31). And if each effect returned a cleanup, on the click you would see cleanup NO DEP → cleanup VALUE → NO DEP → VALUE: all cleanups for that pass run before any of the new effects.

52. The box model and box-sizing

What is the CSS box model, and how does the box-sizing property change how width and height are calculated?

Plain version: think of a framed picture. The photo is the content, the white mat around it is the padding, the frame is the border, and the empty wall around it is the margin. When you say "make it 300 wide", box-sizing decides whether you meant the photo or the whole frame.

How it works

Four layers, inside out: content, padding, border, margin. The default is content-box, where width measures the content only — padding and border are added on top, so the box ends up bigger than the number you wrote.

width: 300px; padding: 20px; border: 2px solid;

content-box (default) → 300 + 40 + 4 = 344px on screen
border-box            → 300px on screen, content shrinks to 256px

So border-box means the number you write is the number you get: padding and border are taken out of the inside instead of added to the outside.

Margin is outside the box either way. No box-sizing value ever counts it in width — it pushes neighbours around, it is not part of the box. And two stacked vertical margins collapse: 20px below one block and 30px above the next gives one 30px gap, not 50px.

What teams actually ship

*, *::before, *::after { box-sizing: border-box; }

Not taste — predictability. Under the default, width: 100% plus any padding overflows its parent, which is most of the "where did this horizontal scrollbar come from" bugs.

If they push

  • min-width, max-width and flex-basis all measure the same box as width.
  • outline and box-shadow take up no space in either mode. That is why outline is the right thing for a focus ring: it can't shift the layout.
  • getBoundingClientRect() and offsetWidth report the border box; clientWidth drops the border and scrollbar.

53. Event order on nested elements

When you click on a nested element, how does the browser decide which event handlers run, and in what order?

Plain version: a parcel is delivered to a room deep inside a building. It travels down through the lobby and the hallways to reach that room, then back out the same way. Anyone along the route can react as it passes — on the way in, on the way out, or both.

One thing to get out of the way: this is not the event loop. The event loop decides when a task runs; propagation decides which elements get a turn at one click, and all of it happens inside a single task (§13 is the other question).

The three phases

  1. Capturing — down from window to the clicked element's parent. Only listeners registered with capture: true fire here.
  2. Target — the clicked element. Its listeners fire in the order they were added.
  3. Bubbling — back up to window. This is where addEventListener puts a listener by default, which is why a parent's handler runs after the child's.
outer.addEventListener("click", () => console.log("outer capture"), true);
outer.addEventListener("click", () => console.log("outer bubble"));
inner.addEventListener("click", () => console.log("inner"));

Those last two are the pair people mix up. On a link, preventDefault cancels the navigation and the click still reaches document; stopPropagation keeps the navigation and hides the click from every ancestor.

Event delegation

Bubbling put to work: one listener on a parent instead of one per row. It also covers rows added later.

list.addEventListener("click", (event) => {
  const row = event.target.closest("[data-id]");
  if (row) remove(row.dataset.id);
});

If they push

  • event.target is what was clicked; event.currentTarget is the element whose listener is running. Delegation is the reason they differ.
  • Not everything bubbles: focus, blur, mouseenter and mouseleave don't. Their bubbling twins are focusin, focusout, mouseover, mouseout.
  • React adds one listener at the root and replays propagation through your components, so onClick still bubbles parent-after-child — but a native stopPropagation outside React's root can swallow the event entirely.

54. A long list that freezes while filtering

A page renders 2,000 items and filters them as the user types in a search box. The UI freezes for a moment on every keystroke. What would you investigate, and what would you try first?

Plain version: searching 2,000 names is fast — faster than a blink. Redrawing 2,000 rows on screen is the slow part. So the answer is to draw less, not to search faster.

Measure before guessing

Record three keystrokes in the Performance panel and look at what fills the long task:

  • One function hogging it → the filter really is expensive (a regex or a new Date() per item).
  • React's commit, 2,000 rows wide → re-rendering the list. This is the usual answer.
  • Layout, Recalculate style, Paint → the sheer number of DOM nodes.

The rough arithmetic is the giveaway: 2,000 string comparisons is well under a millisecond, while 2,000 rows re-rendered and laid out is tens of milliseconds — and anything past ~50ms from keypress to paint feels like a stutter. Say that before naming a fix (§24 is the full version).

Then fix it in this order

  1. Render fewer rows. The screen holds about 20; mounting 2,000 is the bug. Virtualization renders only the visible slice, and the cost stops growing with the data (§35).
  2. Keep typing off the slow path. useDeferredValue lets the input update instantly and the list catch up a frame later. A debounce does the plain version, and it's the right one when each keystroke would fire a request (§26).
  3. Skip work that didn't change. useMemo the filtered array, React.memo the row — which only pays off if the row's props are stable (§22).
  4. Check the keys. key={index} on a reordering list makes React patch every row instead of moving it.

One thing not to say: "use the Virtual DOM". In React it is always on, and it is the thing doing the work you're trying to avoid.

Mention the UX half too, because it's half the grade: with a debounce the list is briefly stale, so show "Searching…" rather than "No results", and put the result count in an aria-live="polite" region so the change isn't silent to a screen reader.

55. Length of the last word

Given a string of words separated by one or more spaces, possibly with leading and trailing spaces, return the length of the last word. There is always at least one.

Plain version: read it backwards. Skip any spaces at the end, then count letters until you hit the next space. Stop.

Work it out

  1. What counts as a word here? A run of characters with spaces (or the end of the string) around it. The last word is the one with nothing but spaces after it.
  2. Try the obvious thing and watch it break. Split on spaces, take the final piece. On "hello world" that gives 5. On "hello world " the final piece is an empty string, and you return 0. The trailing space is the entire difficulty of this problem.
  3. So there are two routes. Clean the ends first and then cut, or never cut at all and read backwards from the end.
  4. If you cut: trim() first so there is no empty piece at the end, and split on /\s+/ rather than " " so a run of several spaces does not leave empty pieces in the middle either.
  5. If you read backwards: walk from the last character towards the front, counting the letters you pass. A space you meet before counting anything is a trailing space, so ignore it; a space you meet after counting means the word just ended, so stop. That single rule handles the trailing spaces without trimming anything, and nothing is allocated.

The one-liner

const lengthOfLastWord = (s) => s.trim().split(/\s+/).at(-1).length;

The trim() is doing the real work — without it, trailing spaces make the last element an empty string and you return 0. Splitting on /\s+/ instead of " " collapses runs of whitespace, so no empty strings land in the middle either.

The version they ask for next

Same idea, no array allocated:

function lengthOfLastWord(s) {
  let length = 0;

  for (let i = s.length - 1; i >= 0; i--) {
    if (s[i] !== " ") length++;        // inside the word: count it
    else if (length > 0) break;        // the space before it: done
  }                                    // a space with length still 0 is trailing — keep going

  return length;
}

Both are O(n) time. The split builds an array of every word to use one of them; the loop only touches the tail and allocates nothing. At this size it makes no difference — say so, and say you would ship the one-liner unless asked for constant space.

Edge cases worth naming out loud first: trailing spaces ("hello " → 5), several spaces in the middle, a single word with no spaces, and one letter.

56. Client-side routing for a small SPA

The app is one giant component that conditionally renders views based on a boolean flag. How would you design basic client-side routing for a handful of pages — Home, Profile, Settings?

Plain version: a boolean is a light switch. It changes the room, but the address on the front door never changes, so you can't bookmark the room, you can't go Back to it, and you can't text the address to a friend. A router gives every view its own address.

Reaching for React Router is a fine answer, and file-based routes if the app is on Next.js — where each route also gets its own bundle (§23). Then show you know what the library is doing, because that's the actual question.

The three browser pieces

  • history.pushState(null, "", "/profile") — changes the URL with no reload. It fires no event, so you re-render yourself right after.
  • popstate — fires when the user hits Back or Forward. Forget this one and the URL and the UI drift apart.
  • Intercepting link clicks — a real <a href> would do a full page load, so the handler calls preventDefault(). Keep the href: it's what makes cmd-click, middle-click and "copy link" work.

The whole router

const routes = { "/": Home, "/profile": Profile, "/settings": Settings };

function useRoute() {
  const [path, setPath] = useState(() => location.pathname);

  useEffect(() => {
    const onPop = () => setPath(location.pathname);
    addEventListener("popstate", onPop);
    return () => removeEventListener("popstate", onPop);
  }, []);

  const navigate = (to) => {
    history.pushState(null, "", to);
    setPath(to);              // pushState fires nothing, so tell React
  };

  return [path, navigate];
}

function App() {
  const [path, navigate] = useRoute();
  const View = routes[path] ?? NotFound;

  return (
    <div onClick={(e) => {
      const link = e.target.closest("a[href^='/']");
      if (!link || e.metaKey || e.ctrlKey || e.button !== 0) return;
      e.preventDefault();
      navigate(link.getAttribute("href"));
    }}>
      <nav><a href="/">Home</a><a href="/profile">Profile</a></nav>
      <View />
    </div>
  );
}

What gets added as it grows: dynamic segments like /profile/:id (the object lookup becomes a match loop), React.lazy per route, nested routes for a shared layout.

Two things almost nobody mentions

  • The server has to cooperate. Refreshing on /profile asks the server for that path, and unless it rewrites unknown paths to index.html the user gets a 404. Hash routing (#/profile) exists to avoid needing that.
  • Navigation has to be announced. A route change doesn't reset scroll or move focus, so a keyboard user stays parked in the old page and a screen reader says nothing. Scroll to top, focus the new heading, update document.title.

57. A shared component library

Buttons and inputs are copy-pasted across pages, so styling and behaviour have drifted. How would you structure a simple shared component library — buttons, inputs, cards — for several pages in the same app?

Plain version: every page writes the button by hand, so no two are quite alike. You want a stamp instead of a signature: carve it once, press it everywhere, and when the design changes you re-carve one stamp.

The short answer: one ui/ folder inside the app, one folder per component, and a single index.ts that everything imports from. Design tokens — colour, spacing, radius, type — live in CSS variables and are the only place a raw value appears. Every variation a page needs goes through typed props (variant, size), never through a class name passed in from outside, so there is exactly one way to render a secondary button. Accessibility lives inside the components rather than in the pages using them. Then one page that shows every variant side by side, so drift is visible before it ships.

That is the whole design. The rest is how each piece is built.

The shape on disk

src/ui/
  tokens.css        # the design tokens
  index.ts          # the only entrance: export { Button } from "./Button";
  Button/
    Button.tsx
    Button.module.css
    Button.test.tsx

One folder per component, one barrel file as the public surface. A folder in the app is the right size here — a separate package buys nothing until a second app needs it.

Tokens, not values

Every hardcoded #2d7ff9 is a future inconsistency. Declare the raw values once, then give them roles, and let components use only the roles:

:root {
  --color-blue-500: #2d7ff9;                /* the raw value */
  --color-accent: var(--color-blue-500);     /* the role components use */
  --space-2: 8px;
  --radius-md: 8px;
}

That indirection is what turns a theme or a dark mode into a token swap instead of a find-and-replace.

Props are the contract

type ButtonProps = {
  variant?: "primary" | "secondary" | "ghost";
  size?: "sm" | "md";
} & React.ButtonHTMLAttributes<HTMLButtonElement>;

export const Button = forwardRef<HTMLButtonElement, ButtonProps>(
  function Button({ variant = "primary", size = "md", ...rest }, ref) {
    return <button ref={ref} className={`${styles.button} ${styles[variant]} ${styles[size]}`} {...rest} />;
  },
);
  • The unions make a wrong variant a type error instead of an unstyled button, and the defaults mean a bare <Button> is already right.
  • ...rest plus the native prop type gives you type="submit", disabled, onClick and aria-* without listing them.
  • forwardRef keeps the element reachable for focus and tooltips. It's the most commonly missed piece in a homegrown library.

Put the accessible defaults inside the components too: Input owns the label-to-input link and its error wiring, Button owns the focus ring. That's correctness nobody can forget to copy.

Keeping it from rotting

  • Nothing app-specific gets in. No fetching, no store, no router import, no product copy — a component that imports a feature isn't shareable any more.
  • Test behaviour, not markup. The click fires, the disabled button doesn't, the label points at the input. DOM snapshots only punish restyling.
  • One page showing every variant — Storybook or a plain /ui route. Side by side is how drift becomes visible.
